# 测试架构与 Mock

## 推荐目录

```text
host_validation/
├── run_test.py
├── test.c
├── mocks/
├── dummy_include/
├── fixtures/
├── build/          # 可清理的临时产物
└── logs/
```

不要要求所有工程采用同一目录名；核心要求是与业务源码隔离、可重复生成和容易清理。

## `test.c` 规则

- 提供完整 `main()`，以独立函数组织用例。
- 通过头文件或 `extern` 引用业务符号，不包含业务 `.c`。
- 每个用例独立复位全局状态与 Mock，避免依赖执行顺序。
- 断言同时显示表达式、期望值和实际值。
- 对数组、报文或内存块给出首个差异位置，不只输出“不相等”。

## Mock 设计

按接口语义选择最小模型：

- 寄存器：内存镜像，并记录读写地址、宽度和顺序。
- 收发接口：输入队列加输出捕获队列。
- 时间：可推进的虚拟 tick，禁止依赖真实睡眠。
- EEPROM/Flash：带范围检查的字节或目标字宽数组。
- 中断/DMA：显式触发回调或完成事件，不模拟无关硬件细节。

Mock 应允许测试注入错误、超时、短包、边界值和重复调用。不要让 Mock 自动返回“成功”而掩盖调用参数错误。

## Runner 职责

`run_test.py` 应：

1. 创建或清理本次专用构建目录。
2. 复制需要适配的源码，不改原文件。
3. 生成或选择最小 dummy header。
4. 显示完整编译命令并捕获 stdout/stderr。
5. 编译失败立即返回非零。
6. 运行测试程序，保存完整日志并转发退出码。
7. 在报告中列出生成物位置。

如果工程已有 CMake、Meson、Ceedling 或 Unity 等测试框架，优先复用现有框架，不要强行生成 Python runner。
