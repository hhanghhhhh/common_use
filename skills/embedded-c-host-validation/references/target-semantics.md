# 目标语义与主机适配

## 先从工程取证

优先检查：

- 编译器及 CPU 参数；
- `typedef` 和平台头文件；
- 链接命令文件与内存模型；
- 结构体 packing、位域和对齐选项；
- 序列化代码中的显式移位与长度单位。

不要仅凭目录名猜测目标是 C2000、STM32 或其他平台。

## 常见差异

- `char`、`int`、`long` 和指针宽度；
- `char` 是否为最小 8 位寻址单位；
- `sizeof(Uint16)` 与协议“字节长度”的关系；
- 大小端、未对齐访问和结构体 padding；
- 位域布局与编译器扩展；
- `volatile`、原子性、中断并发和 DMA 可见性。

涉及协议帧或持久化布局时，优先用固定宽度类型和显式编码/解码验证，不依赖主机结构体直接映射。

## dummy header 原则

dummy header 只包含测试所需的：

- 类型和常量；
- 最小结构体声明；
- 必要 extern；
- 无副作用的硬件宏替身。

不要复制完整厂商 SDK，也不要随意改变业务条件编译路径。若 dummy 定义决定了业务行为，应把该定义列入测试证据。

## 硬件实现剥离

真实寄存器访问导致 GCC 无法编译时，可在临时副本中剥离对应函数，并由 Mock 提供同名接口。必须保证：

1. 只替换硬件边界，不重写被测算法。
2. 记录替换的函数和原因。
3. 将真实目标编译与下板行为列为未覆盖范围。

## `-fcommon`

`-fcommon` 可帮助旧式工程兼容多个 tentative definition，但也可能隐藏头文件中错误定义全局变量的问题。先在默认模式下编译；只有确认这是目标工具链的既有语义时才启用，并同时报告重复定义风险。
