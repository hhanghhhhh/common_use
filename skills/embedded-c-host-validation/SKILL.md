# 嵌入式 C 主机侧验证

目标是在不修改业务源码的前提下，用可复查的主机测试证明指定逻辑是否正确。主机测试不能替代目标编译器、真实寄存器、时序和硬件联调。

## 一、先确认测试边界

1. 从工程文件、编译参数、类型定义和链接配置识别目标平台；无法可靠判断时再询问用户。
2. 明确被测模块、入口函数、输入、可观察输出和通过条件。
3. 区分纯业务逻辑与寄存器、ISR、DMA、通信外设等硬件依赖。
4. 确认目标机的最小寻址单位、整数宽度、字节序、对齐和结构体布局。
5. 将真实目标编译与下板验证列为独立证据，不把 GCC PASS 等同于固件下板 PASS。

目标语义存在差异时，读取 [target-semantics.md](references/target-semantics.md)。

## 二、建立隔离测试目录

- 在工程内新建专用验证子目录；不要把生成文件散落到源码目录。
- 保持原始业务源码只读。需要适配时，复制到临时构建目录后再修改副本。
- 将测试、Mock、dummy header、构建产物和日志限制在该目录内。
- 使用 UTF-8 保存新增文本文件。

推荐结构和 Mock 组织方式见 [test-harness.md](references/test-harness.md)。

## 三、构建测试闭环

1. 先用目标编译器对改动文件做快速编译检查；TI C2000 工程可从现有 `subdir_rules.mk` 与 `subdir_vars.mk` 提取真实参数。需要完整 CCS 构建时改用 `ccs-c2000-debug`。
2. 为缺失硬件头建立最小 dummy header，只声明当前测试实际需要的类型、宏、结构体和 extern。
3. 在独立 `test.c` 中提供完整 `main()`；只用 `extern` 引用业务函数和变量，禁止 `#include` 业务 `.c`。
4. 用可注入、可捕获的 Mock 替代底层接口。通信接口优先使用队列、环形缓冲或内存镜像。
5. 每个用例按“Mock 复位 → 状态初始化 → 注入输入 → 触发运行 → 断言输出”执行，并保证用例互不污染。
6. 让 runner 创建临时目录、准备副本、编译、运行、保存日志并返回正确退出码。
7. 先运行聚焦用例，再运行覆盖该模块的完整回归。

## 四、编译与失败规则

- GCC 基线使用 `-std=c99 -Wall -Wextra`，按工程需要增加 include、define 和 sanitizer。
- 只有确认旧工程依赖 tentative definition 合并时才加 `-fcommon`，并在报告中说明；不要用它掩盖真正的重复定义。
- 编译失败时输出完整命令和 stderr，停止运行测试。
- 测试失败时保留输入、关键状态、期望值、实际值和完整日志，进程返回非零。
- 临时剥离硬件实现时，只改构建副本，并记录改动；不得悄悄改变被测业务逻辑。

## 五、验收与报告

至少分别报告：

1. **目标编译证据**：是否用真实目标编译器检查，检查范围是什么。
2. **主机构建证据**：GCC 命令、警告和产物。
3. **测试证据**：用例数、通过/失败、关键输入输出和 Mock 交互。
4. **语义差异**：主机与目标机在类型、布局或硬件行为上的未覆盖风险。
5. **最终结论**：PASS、FAIL 或 BLOCKED，以及下一步应做的目标机验证。

日志格式与判定细节见 [evidence-reporting.md](references/evidence-reporting.md)。
